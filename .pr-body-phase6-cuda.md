## Summary

- Gate the existing CUDA → Vulkan → CPU order on a local `nvidia-smi --query-gpu=name` probe. CUDA is attempted only when `binaries/cuda/llama-server.exe` is present and `nvidia-smi` reports a GPU. A missing tool, non-zero exit, empty output, or a 3-second timeout skips CUDA and leaves Vulkan then CPU unchanged. `start_serialized` and the Vulkan implicit-layer env vars are untouched. Chat `StatusPill` still says only "Running locally" / "Engine: llama.cpp".
- Pin the official llama.cpp `b9859` CUDA 12.4 artifacts in `scripts/packaging/fetch-llama-server.ps1`, with SHA-256 values taken from the published release digests. The script verifies `llama-b9859-bin-win-cuda-12.4-x64.zip` and merges DLLs from `cudart-llama-bin-win-cuda-12.4-x64.zip` into `binaries/cuda` so the variant does not need a separate CUDA Toolkit. `-SkipCuda` still fetches only Vulkan and CPU. Binaries stay gitignored.
- Advanced Diagnostics names CUDA when that variant is active (`GPU acceleration (CUDA)` / `GPU (CUDA)`). A CPU fallback whose first failure is CUDA now says CUDA was tried, then Vulkan, instead of describing the attempt as Vulkan-only.

Branched from `fix/model-activation-race-and-chat-binding` (`83813df`). Rebase onto `main` after PR #36 merges before opening this pull request.

### Note for reviewers

With the CUDA variant present, `tests/runtime_spikes.rs` must be run with `--test-threads=1`, as its module header already documents. Under the default parallel run, several CUDA `llama-server` processes initialize at once and `spike_cancellation_on_disconnect` can exceed its 30-second request timeout on an 8 GB card. Serially the same six tests pass in about 10 seconds. This is host GPU contention in the spike harness, not a change in runtime behavior.

### Not covered here

- Non-NVIDIA hardware was simulated by removing the CUDA binary, not by testing on an AMD or Intel-only machine. The `nvidia-smi`-absent branch is covered by unit tests rather than by a machine without the tool installed.
